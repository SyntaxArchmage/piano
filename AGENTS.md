# Repository Guidelines

1. Make the smallest change that satisfies the request; prefer surgical edits over rewrites or broad cleanup.
2. Inspect the current state and read the affected code and its callers before designing changes.
3. Preserve unrelated work and existing user changes: leave unrelated test suites alone, and commit only requested work, excluding unrelated or sensitive files.
4. Avoid unnecessary dependencies and cross-layer coupling.
5. Keep compatibility boundaries explicit during migrations: new and old interfaces live in separate modules; old entry points delegate to the new implementation and carry a deprecation marker.
6. Keep new code cohesive, simple, and independently understandable, with clear, consistent names that communicate ownership and purpose.
7. Leave unfinished behavior clearly marked and safely disabled.
8. Add focused tests for new behavior and boundaries.
9. Verify before committing with `npm run typecheck && npm run lint && npm test`. GitHub CI runs the same sequence on every push and pull request; narrow the gate only when the developer says so.
10. Review the complete diff and repository status before committing.
11. Push only when explicitly requested; pushes use the configured `origin` remote.
12. Discuss every discovered issue, ambiguity, or scope change with the developer. Confirm before irreversible or scope-changing decisions, and record design tradeoffs (public interfaces, data models, cross-package boundaries) in the task or PR description.
13. Write commit messages that state what changed and why, with no AI attribution: the commit-msg hook rejects `Co-Authored-By:` trailers and "generated by" lines naming an AI tool. Keep each message short and readable: one subject line of at most 72 characters, plus a body of at most a few lines only when the why needs stating — no walls of text.
14. Keep AGENTS.md and CLAUDE.md byte-identical on every edit.
15. Project skills live as four real copies — `.agents/skills/` (canonical), `.claude/skills/`, `.codex/skills/`, `.github/skills/`. Keep every copy's SKILL.md identical; never use symlinks.
16. `TASTE.md`, `REVIEW.md`, `REFACTOR.md`, and `SPEEDUP.md` at the repo root are skill local state, intentionally untracked. Leave them out of commits and unrelated cleanup.
17. Think in English internally, but write responses to the developer in Chinese. The language rule covers prose only: identifiers, paths, commands, option labels (A/B/C), and established technical terms keep their original form — never translate them into Chinese.
