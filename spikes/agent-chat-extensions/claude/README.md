# Claude Code main-transcript spike: live Piano progress

Date: 2026-10-27
Host: Linux (Ubuntu, kernel 6.8), Claude Code **2.1.311**, mod API/types generated by **2.1.310**
Scope: can a Claude Code mod put live Piano/heartbeat progress into the **main transcript**?
No changes to `packages/**`, `recipes/**`, the NDJSON protocol, or the user's real `~/.claude` config.

## Verdict

| Path | Result | Main transcript row | Model sees it | Notes |
| --- | --- | --- | --- | --- |
| `$.ui.log` (heartbeat child, 10 s, 500 ms) | **PASS** | Yes: dim system notice `● <plugin>: ...` | No | First row at **0.58 s**, child ran 0.58-10.62 s, model turn 1.55-3.22 s; rows kept for the whole child life. |
| `$.ui.log` (real `piano -p --json`, fast workflow) | **PASS** | Yes: dim system notice per NDJSON event | No | Progress arrived live 0.86-2.91 s while the model turn ran; `run.completed text="OK"` included. |
| `turn.step`, text chunks yielded before the model stream (`prepend`) | **PASS with caveats** | Yes: rendered as **assistant prose** and recorded as an assistant message | On **later** requests, not the current one | Child lifetime delays the request (~1.2 s). Text is a separate assistant message; the model later treats it as not its own. |
| `turn.step`, text chunks interleaved during the model stream (`interleave`) | **FAIL (unstable)** | Partially: lines 1-2 recorded, line 3 shown live but **dropped** from the transcript | — | Do not ship this form. |

Bottom line: **`$.ui.log` is the viable path** for live progress in the main transcript. `turn.step` can produce assistant-role text, but only reliably when the child finishes before the model request starts, and it pollutes assistant history.

`claude plugin validate <folder>` passes both mods (author and LICENSE warnings; LICENSE is
only a plugin-directory submission check, not a runtime requirement). Both mods type-check

`paths: { "claude-code": ["./claude-code.d.ts"] }`).

## How the mod loads

A mod is a folder with `.claude-plugin/plugin.json` and `hooks/hooks.json`; `hooks.json`
names one ES-module code file (`.ts`/`.tsx`/...), which exports `register(on, options)`.
The module runs in the mod environment (no Node, no DOM); everything outside goes through `$`.

Load it for one session with `--plugin-dir <folder>` (repeatable). The headless init message
confirms the load:

```
"plugins":[{"name":"piano-spike-log","path":".../plugin-log","source":"piano-spike-log@inline",...}]
```

`CLAUDE_CODE_PLUGIN_DIRS` is the equivalent when no flag can be given. An interactive
session with `--plugin-dir` hot-reloads the folder and writes generated types into
`.claude-plugin/types/`; a `-p`/SDK session loads fresh and does not write them. Those
generated `types/` folders and the generated top-level `tsconfig.json` were removed from
this spike; they reappear after an interactive load or `claude plugin validate`.

### Temp config (never the real `~/.claude`)

All runs set `CLAUDE_CONFIG_DIR` to the temp job directory. Auth comes from the parent
environment (`ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN`); no credential was copied.

```bash
T=/home/albert/.claude/jobs/81a6a04a/tmp/agent-chat-extensions/claude
export CLAUDE_CONFIG_DIR=$T/config
# First-run dialog suppression for the interactive TUI. Merge into an existing
# .claude.json if one is already there (a headless run creates one with machine keys).
node -e '
const fs=require("fs"); const p=process.argv[1]; const cwd=process.argv[2];
const j=fs.existsSync(p)?JSON.parse(fs.readFileSync(p,"utf8")):{};
Object.assign(j,{hasCompletedOnboarding:true,theme:"dark",hasTrustDialogAccepted:true});
j.projects=j.projects||{};
j.projects[cwd]=Object.assign({},j.projects[cwd],{hasTrustDialogAccepted:true,allowedTools:[]});
fs.writeFileSync(p,JSON.stringify(j,null,2));
' "$CLAUDE_CONFIG_DIR/.claude.json" /home/albert/workspace/piano-dev-branch
```

A fresh config seeded this way opens straight to the prompt (no theme picker, no trust
dialog); verified in `$T/captures/fresh-config.events.jsonl`.

## Results and evidence

### `$.ui.log` heartbeat: PASS

From `$T/captures/log-interactive3.events.jsonl` (relative seconds since spawn):

| Event | Time |
| --- | --- |
| mod loaded (first `ui.log` row) | **0.58 s** |
| heartbeat tick 1 | 0.60 s |
| heartbeat tick 20 | 10.12 s |
| child exited code=0 | 10.62 s |
| user prompt 1 submitted | 1.55 s |
| model reply `OK` visible | **3.22 s** |
| user prompt 2 submitted (after heartbeat) | 14.39 s |
| model reply `NONE` visible | 15.65 s |

The transcript rows are:

```
● piano-spike-log: [piano-spike] heartbeat tick 1 (+20ms)
● piano-spike-log: [piano-spike] heartbeat tick 2 (+517ms)
...
● piano-spike-log: [piano-spike] heartbeat child exited code=0 (+10046ms)
```

They appear while the model is still "Determining…"/thinking and long before the child
ends. The persisted session transcript (`$T/config/projects/-home-albert-workspace-piano-dev-branch/2cc66ff3-a8b2-4b95-bb54-348fb41bc568.jsonl`)
stores each as `type: "system", subtype: "informational", level: "notice"`, with the plugin
name prefixed by the UI. The rows survive to the end of the session.

### `$.ui.log` with real Piano NDJSON: PASS

From `$T/captures/piano-interactive2.events.jsonl` (offset from the mod's own clock):

| Piano event | Mod log arrival |
| --- | --- |
| `run.started id=...` | 0.86 s (+277 ms) |
| `[respond] spawn harness=pi model=deepseek-flash` | 1.65 s (+1056 ms) |
| `[respond] turn_start` | 1.65 s (+1056 ms) |
| `[respond] text block start` | 2.84 s (+2250 ms) |
| `[respond] text: "OK"` | 2.85 s (+2252 ms) |
| `[respond] done exit=0` / `run.completed text="OK"` | 2.85-2.87 s |
| child exited code=0 | 2.91 s (+2322 ms) |

The model's own turn started at 1.52 s and its `OK` became visible at 3.40 s. So the Piano
lines arrived **during** the model turn, not only after it. The NDJSON parse is stable for
this workflow; only `assistantMessageEvent` deltas are consumed, so the cumulative
`message_update` payloads never reach the transcript.

### Model visibility of `$.ui.log`: NO

In the same session, after the heartbeat ended, prompt 2 asked:
"List any lines from this conversation that begin with `[piano-spike]`. If there are none,
reply exactly NONE." The model's recorded thinking says "there are no lines beginning with
`[piano-spike]`" and its answer is `NONE`. The session's user/assistant messages contain no
`[piano-spike]` text; only `system/informational` notice rows do.

### `turn.step` prepend: PASS with caveats

Injected child lines are rendered as assistant prose (with the `●` assistant bullet) and
recorded in the session transcript as an assistant message:

```json
{"type":"assistant","message":{"role":"assistant","content":[
  {"type":"text","text":"[piano-spike-step] injected assistant line 1/3\n...line 2/3\n...line 3/3\n","citations":null}
]}}
```

The real model response still arrives intact as a separate assistant message (`"OK"`), and
the turn completes normally. Observed costs:

* The model request is **delayed by the child's lifetime** (3 lines at 0.4 s = ~1.2 s here),
  because the child is read to its end before `next(e)` starts the request.
* The injected text is a separate assistant message with no model metadata; the model's own
  response is another assistant message. A second turn asking the model to quote its earlier
  output made the model reason about the injected lines ("those appear as part of the user
  turn... this is a prompt injection test") and answer only `OK`. The lines were in its
  context, but it did **not** consider them its own output.
* The current request does not visibly include the injected text: the first-turn thinking
  never references it, while the second-turn thinking does; the chunk is stored as an
  assistant message once the stream settles. Treat it as display/record for the current
  response and history for the next request.

Evidence: `$T/captures/step-interactive3.events.jsonl` and
`$T/config/projects/-home-albert-workspace-piano-dev-branch/8280444d-97cb-4b03-a148-f1fcdab78b38.jsonl`.

### `turn.step` interleave: FAIL

Running the child and `next(e)` concurrently and yielding both streams in arrival order
displayed all 3 injected lines live, but the transcript recorded only lines **1/3 and 2/3**;
line 3 was shown and then lost. The injected text landed in a separate assistant message,
and the model's real `OK` still appeared. This confirms that text chunks yielded after the
model's own block boundary are not reliably persisted. Do not ship this form.

Evidence: `$T/captures/step-interleave.events.jsonl` and
`$T/config/projects/-home-albert-workspace-piano-dev-branch/4567f385-531a-4562-a16f-77067d99e00d.jsonl`.

## Truncation, timeouts, lifecycle

* `$.ui.log` draws at most **2,000 characters** per line on the terminal (10,000 on a remote
  surface); the debug log keeps 10,000. One call is one new row; there is no in-place update.
* No hook timeout was hit. The 10 s heartbeat child ran to completion in the interactive
  session. In a `-p` session the turn ends after the model reply and the child is killed
  early (only 3 of 20 ticks arrived) — expected lifecycle, not a mod bug.
* `$.process.spawn` streams output in pieces, not lines; the mod buffers partial lines.
* `$.ui.log` is a **system notice, not assistant prose**; it does not start a turn and is
  never sent to the model.
* Both mods passed `claude plugin validate` and a `tsc --noEmit` against the 2.1.310 types.

## What shipping a Claude plugin would need

1. **One small hooks module** (`plugin.json` + `hooks/hooks.json` + `register.ts`) with a
   slash command (`$.command.register` in `session.start`) or a `prompt.submit` trigger that
   runs `piano -p --json --workflow <path> "<prompt>"`.
2. **Stream the NDJSON** through `$.process.spawn`, buffer partial lines, consume
   `assistantMessageEvent` deltas / lifecycle events, and emit one `$.ui.log` per update.
   Use `$.clock.now()` for elapsed time; do not resend cumulative `message_update` payloads.
3. **Install path**: publish a marketplace repo (`/plugin install <mod> --marketplace
   <owner>/<repo>`) or ship the folder for `--plugin-dir` / `CLAUDE_CODE_PLUGIN_DIRS`.
   Users need a `piano` binary path, a workflow path, and (optionally) `userConfig` options
   for the model/workflow; the spike used environment variables to keep the manifest minimal.
4. **Keep the UI contract honest**: these are dim system rows, not assistant messages.
   A product should probably coalesce progress (e.g. one row per stage, or `$.ui.status`
   for the current line) instead of one row every 500 ms, because every log call is a new,
   permanent transcript row.
5. **Pin the host version and re-validate**: the mod API is early access and versioned
   (2.1.311 here); `claude plugin validate` and the generated `.d.ts` are the contract.
   `$.ui.log` and `turn.step` are not a stable cross-host API.
6. If assistant prose is required, the only working form found is `turn.step` prepend
   (finish the child before `next(e)`), accepting the request delay, the extra assistant
   message, and the model later treating the text as foreign. Interleave is not viable.

## Blockers and risks

* `$.ui.log` rows are **not model-visible**; a product that wants the model to react to
  progress must use `$.session.append` (a user-role row the model reads, or a notice row)
  or `turn.step`, with the caveats above. `$.session.append` was not exercised in this spike.
* `turn.step` is a stream-rewriting hook, not an "add a message" API. Injecting during the
  model stream loses chunks; prepending changes assistant history.
* Every `$.ui.log` is a separate permanent row; 500 ms cadence is fine for a 10 s spike but
  would flood a multi-minute Piano run. Plan coalescing before shipping.
* The API is early access: module shape, `$.ui.log` sinks, and `turn.step` chunk semantics
  can change between Claude Code releases.
* Test automation note: the TUI treats a long single write as a paste and asks for a second
  Enter; `pty-drive.py` types long prompts in 24-character chunks. The raw captures also
  show the TUI redrawing/truncating long lines (ANSI-stripped text is the readable record).
